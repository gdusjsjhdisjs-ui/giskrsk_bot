## 2. Контекст продукта

«ГИС Красноярье» — Telegram‑бот и WebGIS‑карта для первичной проверки земельных участков, зон ПЗЗ, генплана, красных линий, кадастровых слоёв и ЗОУИТ.

### Текущий стек

- Карта: MapLibre GL JS 4.7.1.
- Frontend: чистые JavaScript, HTML, CSS; основной интерфейс находится в одном `webapp/index.html`.
- Геоданные: локальные GeoJSON и TMS NextGIS GeoServices.
- Backend: Python, aiogram, FastAPI, SQLAlchemy, Redis/ARQ, NextGIS API, DeepSeek через OpenAI‑совместимый клиент.
- Разработка WebApp: Node.js; публикация статической части возможна на GitHub Pages.
- PDF: WeasyPrint/Jinja2.

### Уже реализовано

- ПЗЗ Красноярска, Дивногорска и Емельяновского района.
- Генплан Красноярска и красные линии.
- Кадастровые кварталы, участки и ЗОУИТ через TMS.
- Подложки: светлая, тёмная, OSM, спутник, 2ГИС.
- Управление слоями и прозрачностью.
- Поиск населённых пунктов через Nominatim.
- Геолокация.
- Измерение расстояния и площади.
- Клик по объекту и информационная шторка.
- Заказ вырезки геоданных.
- Магазин и подписки.
- Telegram AI‑консультант на DeepSeek.
- Проверка участка, пакетная обработка, мониторинг и PDF‑отчёты.

### Важный принцип

AI не является источником официальных данных. AI объясняет и объединяет факты, которые предварительно получены из NextGIS, локальных GeoJSON, документов ПЗЗ и детерминированных GIS‑расчётов.

## 3. Правила безопасности — обязательно

1. API‑ключ, опубликованный в переписке или документации, считать скомпрометированным. Попросить владельца отозвать и выпустить новый ключ.
2. DeepSeek API key, NextGIS bearer token, YooKassa key и Telegram bot token хранить только в `.env`/secret manager на backend.
3. Никогда не вставлять DeepSeek API key в `index.html`: GitHub Pages полностью публичен.
4. Frontend обращается только к нашему FastAPI endpoint, например `/api/ai/chat`.
5. Ограничить CORS доменами WebApp и локальной разработки; не использовать `allow_origins=["*"]` в production.
6. Ограничить размер вопроса и загружаемых файлов, MIME‑типы, число страниц и частоту запросов.
7. Логи не должны содержать токены, пароли, полные персональные данные и полный текст закрытых документов.
8. Не возвращать пользователю внутренний текст исключений API. Возвращать безопасное сообщение и `request_id`.
9. Перед отправкой документов во внешний LLM предупреждать о передаче данных и при необходимости обезличивать текст.

## 4. Главная цель AI‑ассистента

Сделать не общий чат «про землю», а помощника, который умеет:

1. Понять цель пользователя.
2. Найти участок, зону или документ.
3. Получить реальные данные через инструменты.
4. Найти подходящие фрагменты документации.
5. Выполнить геоанализ.
6. Сформировать структурированный ответ с источниками.
7. Явно показать неизвестные данные и следующие шаги.

### Рекомендуемый формат ответа

- **Короткий ответ** — 1–3 предложения.
- **Найденные факты** — только подтверждённые значения.
- **Предварительный вывод** — понятное объяснение.
- **Ограничения и риски** — чего нельзя утверждать.
- **Источники** — документ, редакция, страница/пункт или слой, дата данных.
- **Что проверить дальше** — конкретный список действий.

Нельзя писать «строить разрешено» только по названию зоны. Корректная формулировка: «по доступным данным объект попадает в зону X; для подтверждения необходимо проверить регламент, основные/условно разрешённые ВРИ, параметры строительства, ЗОУИТ и актуальный ГПЗУ».

## 5. Архитектура AI‑ассистента

### 5.1. Конвейер запроса

```text
Вопрос пользователя
  ↓
Intent Router: участок / зона / документ / сравнение / карта / общий вопрос
  ↓
Entity Extractor: кадастровый номер, координаты, муниципалитет, тип документа, цель
  ↓
Tool Layer:
  - поиск участка в NextGIS
  - point-in-polygon по ПЗЗ
  - пересечения с ЗОУИТ/красными линиями
  - буфер 100 м и соседние зоны
  - поиск по базе документов
  ↓
Evidence Pack: факты + ссылки + даты + confidence
  ↓
DeepSeek: только объяснение на основе Evidence Pack
  ↓
Verifier: проверка цитат, чисел, обязательных полей и противоречий
  ↓
Telegram / WebApp / PDF
```

### 5.2. Разделение ответственности

**Выполнять кодом:**

- преобразование EPSG;
- area/length;
- point‑in‑polygon;
- intersection/buffer/distance;
- валидация кадастрового номера;
- проверка GeoJSON;
- сортировка, фильтрация, расчёт цен;
- получение объектов через API.

**Выполнять LLM:**

- классификация намерения;
- извлечение сущностей из свободного текста;
- объяснение нормативных терминов;
- краткое резюме найденных документов;
- сравнение подтверждённых фактов;
- создание понятного чек‑листа;
- формирование ответа в заданной структуре.

LLM не должен «дорисовывать» отсутствующие координаты или придумывать разрешённые виды использования.

## 6. Сценарий «Найди документацию»

### 6.1. Примеры запросов

- «Найди документ, где указана максимальная высота в зоне Ж‑1».
- «Какие документы регулируют участок 24:11:0330102:814?»
- «Найди решение об изменении ПЗЗ по Емельяновскому району».
- «Покажи пункт про минимальный отступ от границы участка».
- «Сравни редакции ПЗЗ 2024 и 2026 года».

### 6.2. MVP без сложной векторной БД

1. Создать каталог `knowledge/documents/`.
2. Для каждого документа хранить метаданные:
   - `document_id`;
   - название;
   - муниципалитет;
   - тип документа;
   - дата утверждения;
   - номер решения;
   - редакция;
   - статус: действующий/архивный/не подтверждён;
   - URL источника;
   - дата загрузки;
   - SHA‑256 файла.
3. Извлечь текст PDF через `pypdf`/`PyMuPDF`; для сканов — OCR.
4. Разбить текст по заголовкам и страницам, а не только по фиксированному количеству символов.
5. На первом этапе использовать PostgreSQL full‑text search или SQLite FTS5.
6. После стабилизации добавить embeddings + pgvector и гибридный поиск: BM25/FTS + vector.
7. Возвращать 5–10 фрагментов, затем rerank.
8. DeepSeek получает только найденные фрагменты и обязан цитировать `document_id`, страницу и пункт.

### 6.4. API поиска документации

```python
# app/api/ai.py
from fastapi import APIRouter, Depends
from pydantic import BaseModel, Field

router = APIRouter(prefix="/api/ai", tags=["ai"])

class DocumentSearchRequest(BaseModel):
    query: str = Field(min_length=3, max_length=1000)
    municipality: str | None = None
    document_type: str | None = None
    current_only: bool = True

@router.post("/documents/search")
async def search_documents(payload: DocumentSearchRequest):
    # Реализацию внедрять через сервис и репозиторий, а не прямо в роутере.
    hits = await document_search_service.search(
        query=payload.query,
        municipality=payload.municipality,
        document_type=payload.document_type,
        current_only=payload.current_only,
        limit=8,
    )
    return {"hits": [hit.model_dump() for hit in hits]}
```

## 7. Улучшение существующего AI‑консультанта

### 7.1. Критические улучшения

1. Перед ответом распознавать кадастровый номер регулярным выражением.
2. Если номер найден — сначала вызвать `ParcelService`, затем GIS‑инструменты и поиск документов.
3. Передавать модели не вопрос отдельно, а `Evidence Pack`.
4. Снизить `temperature` для аналитических ответов до 0–0.2.
5. Убрать отображение количества токенов из пользовательского ответа; хранить usage в telemetry.
6. Не возвращать пользователю сырой текст исключения DeepSeek.
7. Добавить таймаут, retries с backoff и circuit breaker.
8. Добавить fallback: показать собранные факты без AI‑объяснения.
9. Хранить контекст не как бесконечную историю, а как краткую сессию с выбранным участком и последними источниками.
10. Добавить кнопки обратной связи: «Полезно», «Ошибка в данных», «Нужен специалист».

### 7.2. Схема Evidence Pack

class EvidenceSource(BaseModel):

class ParcelEvidence(BaseModel):

    pzz_zone_code: str | None = None
    pzz_zone_name: str | None = None
    permitted_use: str | None = None
    area_m2: float | None = None

    missing_fields: list[str] = Field(default_factory=list)

## 8. AI‑функции, которые стоит добавить

### 8.1. Высокий приоритет

1. **Умный паспорт участка.** Зона, ВРИ, площадь, ЗОУИТ, красные линии, соседние зоны, актуальность, источники.
2. **Поиск по документации с цитатами.** Вопрос → точный пункт/страница → ссылка на документ.
3. **Чек‑лист due diligence.** Что уже проверено, что отсутствует, какие документы запросить.
4. **Сравнение участков.** Таблица 2–10 участков с рисками и объяснением различий.
5. **Объяснение клика по карте.** «Что означает этот объект/слой/атрибут?» на основе feature properties и справочника.
6. **Умные фильтры естественным языком.** «Покажи жилые зоны без пересечения с ЗОУИТ в пределах…» → валидируемый JSON‑фильтр → выполнение кодом.
7. **Контроль актуальности.** AI объясняет, что изменилось между версиями слоя/документа.

### 8.2. Средний приоритет

8. **Разбор загруженного ГПЗУ/PDF.** Извлечь параметры, ограничения и ссылки на страницы.
9. **OCR схем и сканов.** Распознать легенду/надписи, но требовать ручную проверку геопривязки.
10. **Генератор профессионального отчёта.** Черновик PDF для кадастрового инженера/риэлтора.
11. **Умный мониторинг.** Пользователь описывает интерес: «сообщай об изменениях рядом с участком».
12. **Помощник по слоям.** Советует, какие слои включить под задачу пользователя.
13. **Объяснение ошибок данных.** Почему объект не найден, какой формат нужен, какие альтернативные источники проверить.
14. **Автозаполнение карточки товара/слоя.** Описание состава, территории, формата, даты и ограничений лицензии.

### 8.3. Экспериментальные функции

15. **Сценарии застройки.** Пользователь задаёт тип объекта; система формирует список проверок, но не утверждает разрешённость без норм.
16. **Поиск аналогичных участков.** GIS‑фильтры + объяснение сходства.
17. **AI‑сводка аукционов.** Отбор лотов по критериям, карта, риски, ссылки на первоисточник.
18. **Диалог по карте.** Выделить область и спросить: «что здесь важно?».
19. **Голосовой запрос в Telegram.** Распознавание речи → подтверждение сущностей → инструменты → ответ.
20. **Проактивные подсказки.** После поиска участка предложить 3 следующих полезных действия, не перегружая интерфейс.

## 9. Улучшения WebGIS без AI

AI не заменяет базовый UX. Реализовать отдельно:

1. Кадастровый поиск с серверным proxy и валидацией формата.
2. Легенду зон и фильтры по типам ПЗЗ.
3. Тонкую обводку ПЗЗ: `line-width` около 0.3–0.5 и низкую прозрачность.
4. Подписи зон через корректный glyphs endpoint. CSS‑шрифт сам по себе не решает загрузку glyphs для symbol layer MapLibre.
5. Выделение найденного объекта отдельным source/layer.
6. Кнопку «Скопировать координаты/кадастровый номер».
7. Ссылку, восстанавливающую центр, масштаб, слои и выбранный объект.
8. Снимок карты с учётом `preserveDrawingBuffer: true` либо отдельного рендера; проверить CORS всех raster‑источников.
9. Индикатор актуальности каждого слоя.
10. Режим сравнения двух дат/версий слоя.

### Важное про подписи MapLibre

Параметр `text-font` использует шрифтовые стеки из style `glyphs`. Подключение `@font-face` в CSS не гарантирует работу symbol layer. Сначала проверь текущий style JSON. В production используй собственный или разрешённый glyphs endpoint, например шаблон:

```js
const style = {
  version: 8,
  glyphs: 'https://YOUR_ALLOWED_GLYPHS_HOST/fonts/{fontstack}/{range}.pbf',
  sources: {},
  layers: []
};
```

Не вставляй непроверенный публичный URL. Уточни лицензию, CORS и доступность кириллицы.

## 10. Качество AI: тестирование и метрики

### 10.1. Эталонный набор

Создать минимум 50 проверенных кейсов:

- 15 вопросов по конкретным участкам;
- 10 вопросов по зонам;
- 10 поисков пунктов в документах;
- 5 вопросов с недостаточными данными;
- 5 провокаций на выдумывание;
- 5 конфликтов между редакциями документов.

Каждый кейс хранит ожидаемые источники, допустимые факты и запрещённые утверждения.

### 10.2. Метрики

- Citation precision: доля цитат, реально подтверждающих ответ.
- Groundedness: доля утверждений, присутствующих в Evidence Pack.
- Retrieval recall@5: найден ли нужный фрагмент среди первых пяти.
- Tool success rate: доля успешных вызовов GIS/API.
- Abstention quality: умеет ли AI честно отказаться при нехватке данных.
- Latency p50/p95.
- Стоимость одного ответа.
- Пользовательские «полезно/ошибка».

### 10.3. Автоматические проверки

- каждый `source_id` существует;
- номера страниц присутствуют в метаданных;
- все числа из ответа встречаются в Evidence Pack либо вычислены разрешённым tool;
- при `confidence < 0.6` запрещён категоричный вывод;
- ответ содержит disclaimer для юридически чувствительных запросов;
- ответ не содержит токенов, паролей и внутренних исключений.

## 15. Критерии готовности

Функция считается готовой, если:

- работает на реальных данных и graceful fallback;
- не раскрывает ключи;
- не ломает существующую карту и Telegram‑бота;
- имеет тесты;
- ответ содержит источники и дату;
- AI честно сообщает о нехватке данных;
- все GIS‑расчёты выполняются кодом;
- есть инструкция запуска и ручной сценарий проверки;
- изменения компактны и понятны следующему разработчику.

## 16. Итоговый продуктовый принцип

Пользователь должен получать не «красивый текст от нейросети», а проверяемый рабочий результат:

> **объект на карте → подтверждённые факты → найденные нормы → геоанализ → понятное объяснение → источники → следующий шаг.**

Это и есть главное конкурентное преимущество AI в «ГИС Красноярье».
